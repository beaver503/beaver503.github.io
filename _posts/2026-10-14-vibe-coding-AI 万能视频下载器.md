## 本地运行
### 获取 API Key
项目需要 **1 个必需的 API Key**，另外 1 组为可选。

#### 必需：DeepSeek API Key
DeepSeek 用于 AI 视频总结功能（字幕提取后调用大模型生成总结、思维导图、问答）。

### 配置环境变量
```bash
cd backend
cp .env.example .env
```

用任意文本编辑器打开 `backend/.env` 文件，填入你的配置：

```plain
# ✅ 必填 - DeepSeek API Key，用于 AI 视频总结
DEEPSEEK_API_KEY=sk-你的真实key

# ✅ 必填 - JWT 密钥，用于用户登录认证
# 本地开发可以随便写一个字符串，生产环境请使用强随机值
JWT_SECRET=my-local-dev-secret-123

# 🔧 选填 - Stripe 支付配置（不配置不影响核心功能）
STRIPE_SECRET_KEY=sk_test_你的stripe密钥
STRIPE_WEBHOOK_SECRET=whsec_你的webhook密钥
STRIPE_PRICE_ID_MONTHLY=price_你的价格id

# 🔧 选填 - 前端 URL，Stripe 支付完成后跳转地址
FRONTEND_URL=http://localhost:5173
```

| 字段 | 必填 | 用途 |
| --- | --- | --- |
| `DEEPSEEK_API_KEY` | ✅ 必填 | 调用 DeepSeek 大模型生成视频总结、思维导图、AI 问答 |
| `JWT_SECRET` | ✅ 必填 | 用户登录 Token 的签名密钥，本地开发可随意设置 |
| `STRIPE_SECRET_KEY` | 🔧 选填 | Stripe 支付 API 密钥，不填则支付功能不可用 |
| `STRIPE_WEBHOOK_SECRET` | 🔧 选填 | Stripe Webhook 签名验证密钥 |
| `STRIPE_PRICE_ID_MONTHLY` | 🔧 选填 | Stripe 月度会员的价格 ID |
| `FRONTEND_URL` | 🔧 选填 | 支付完成后跳转地址，默认 `http://localhost:5173` |


⚠️ **注意**：`.env` 文件包含敏感信息，已被 `.gitignore` 排除，不会提交到代码仓库。

### 常见问题
#### Q1：`ffmpeg` 未安装，下载视频报错或画质很低？
**原因**：高清视频的画面和声音是分开的，需要 ffmpeg 合并。

**解决**：

```bash
# macOS
brew install ffmpeg

# Ubuntu / Debian
sudo apt install ffmpeg

# Windows：从 https://ffmpeg.org/download.html 下载，解压后将 bin 目录加入 PATH
```

claude code中，ai会通过内置的task工具自动生成子代理来处理子任务，你不需要做额外配置。你也可  
在。claude .claude/agents/目录下创建自定义的子代理（用markdown文件定义）,给它指定专属的角色描述，工具权限和行为规则。  
不过子代理也有局限，每个子代理的上下文是独立的，它们之间无法直接共享信息，所以不适合有强依赖关系的

干得更快，但工资支出也得跟着涨，而且人多了沟通协调的成本也会上来。

  
使用subagents的注意事项  
subagents虽然强大，但使用时需要注意几个关键问题：

  
注意事项 说明  
任务必须独立 子代理之间无法通信，所以分配的任务不能有先后依赖关系  
避免文件冲突 多个子代理同时修改同一个文件会产生冲突，需要提前规划好文件边界  
控制数量 不要一次开太多子代理，3~5个是比较合理的范围，太多反而会增加并成本  
人工审查结果 每个子代理完成后，主代理会汇总结果，但最终还是要人工确认

  
注意token消耗每个子代理都有独立的上下文，token用量会成倍增加  
一个实用的判断标准：如果两个任务修改的文件完全不重叠，就适合并行；如果它们会改同一个文件的不同部  
分，需要谨慎评估；如果改同一个文件的同一个区域，就必须串行。

下载字幕功能





sse编码的最佳实践  
这个bug的根因是sse在传输过程中丢失了换行符和空格等特殊字符，导致前端拼接出来的markdowm文本格式  
错乱。这是sse开发中一个常见的坑。  
se协议规定每一行数据以data:开头，以换行符结束。如果你的内容本身包含换行符，直接传输就会被sse协  
议"吃掉".  
避免这类问题的常见做法：  
1.json编码：后端将每条消息json序列化后再发送，前端收到后解析。json会自动将换行符转义为ln,  
不会被sse协议干扰  
2.base64编码：对内容进行base64编码传输，前端解码后使用，适合二进制或特殊字符多的场景  
3.自定义分隔符：约定一个不会出现在内容中的分隔符来替代换行符，前端收到后再还原  
本项目最终采用了json编码的方案，后端对sse返回内容进行封装，前端再解封装，从根本上解决了字符丢失  
的问题

## 六、SEO 和 GEO 的推广优化
### SEO vs GEO（Generative Engine Optimization，生成式引擎优化，推广领域概念）
一句话总结：  
**SEO：抢搜索引擎蓝色链接排名；GEO：抢AI大模型回答里面的引用、品牌推荐**

###  SEO（搜索引擎优化）
目标：Google、百度这类传统搜索。

+ 用户：输入关键词 → 搜索引擎返回一堆网页链接
+ 你的目标：网站排在搜索结果前几名，**吸引用户点击你的网页**
+ 手段：关键词、外链、页面标题、网站技术优化
+ 流量路径：搜索页 → 用户点链接 → 访问你的网站

###  GEO（生成式引擎优化）
目标：ChatGPT、Gemini、Perplexity、豆包这类AI问答/生成式搜索

+ 用户：直接提问，AI**直接给出整合好的答案**，不一定点网页
+ 你的目标：让AI在回答时，**引用你的内容、提到你的产品、推荐你的品牌**，把你放进AI生成的那段文字里面
+ 手段：结构化内容、清晰事实、权威信源、统一品牌信息、LLM友好的文本
+ 流量路径：AI读取你的网页资料 → AI回答用户问题，直接推荐你

> 例子：  
SEO：用户搜「海外SaaS收款工具」，你的网站排在Google首页。  
GEO：用户问豆包/Perplexity：“做海外SaaS，有什么收款平台推荐？”，AI回答里直接提到你的产品，引用你的官网信息。
>

### SEO与GEO对比表（推广角度）
| 项目 | SEO | GEO |
| --- | --- | --- |
| 全称 | Search Engine Optimization | Generative Engine Optimization（生成式引擎优化，也常叫AEO答案引擎优化） |
| 争夺目标 | 搜索结果链接排名 | AI回答中的引用与品牌推荐席位 |
| 用户行为 | 用户浏览链接，主动点击进网站 | AI直接输出答案，用户不一定打开网页 |
| 核心考核 | 关键词排名、点击量 | AI引用率、品牌提及、作为可信来源 |
| 关系 | 基础，GEO离不开好的SEO | SEO的补充新渠道，**不能替代SEO** |


### GEO推广实操思路
1. **内容结构化**：产品参数、定价、适用场景、优缺点整理成清晰表格、FAQ，大模型更容易提取信息
2. **事实统一**：全网所有平台（官网、博客、独立评测站）品牌信息保持一致，AI交叉校验会优先采信口径统一的来源
3. **权威信源建设**：多平台发布客观产品介绍、案例，增加可信度，AI更愿意引用
4. **面向问题写内容**：写用户会直接问AI的问句，例如：`海外SaaS收款平台有哪些？Lemon Squeezy和Stripe对比`



GEO目前属于比较新的营销概念，**没有像Google SEO那样确定的官方排名算法**，市场上有不少概念炒作。它是长期内容资产建设，不是几天快速见效的投放。

### 为什么选 SQLite 以及何时该升级
本项目选择 SQLite 是因为它零配置、不需要单独安装数据库服务，一个文件就是整个数据库，非常适合轻量级项目和原型开发。

| 场景 | SQLite | MySQL / PostgreSQL |
| --- | --- | --- |
| 单机小项目、原型验证 | 适合，零配置开箱即用 | 过于笨重 |
| 并发用户 < 100 | 完全够用 | 没必要 |
| 并发用户 > 1000 | 写入锁竞争严重，不推荐 | 推荐升级 |
| 需要多台服务器部署 | 不支持（文件级锁） | 必须使用 |
| 需要复杂查询和事务 | 基本支持，但功能有限 | 更强大 |


一个实用的判断标准：如果你的项目需要“多台服务器同时写数据库”，或者“同时有几百个用户在写入数据”，就该考虑升级到 MySQL 或 PostgreSQL 了。

### 安全保障
1. 幂等性：使用 idempotency_key（基于 user_id + 时间窗口），防止重复创建支付
2. Webhook 签名验证：验证 Stripe-Signature，防止伪造回调
3. 订单状态机：pending → paid → expired，防止重复处理
4. JWT Token：密码 bcrypt 加密，Token 有过期时间
5. HTTPS：生产环境必须 HTTPS（Stripe 要求）

### JWT 和 Session 认证的对比
本项目选择了 JWT 作为用户认证方案，这是两种最主流的认证方式之一。两者的核心区别在于“状态存储在哪里”：

| 对比维度 | JWT（本项目采用） | Session |
| --- | --- | --- |
| 状态存储 | Token 存在客户端，服务端无状态 | Session 存在服务端（内存/Redis） |
| 扩展性 | 天然支持多服务器部署 | 需要共享 Session（如 Redis） |
| 性能 | 每次请求自带 Token，无需查询数据库 | 每次请求需要查询 Session 存储 |
| 安全性 | Token 泄露后无法主动失效 | 可以随时在服务端销毁 Session |
| 适用场景 | 前后端分离、移动端、微服务 | 传统服务端渲染的 Web 应用 |


JWT 更适合本项目这种前后端分离的架构，因为前端和后端是独立部署的，用 JWT 不需要在服务端维护状态，实现起来更简单。
